# critic

## Git is an attack surface BEFORE any scanner runs: clone/checkout-time RCE bugs, option injection via locators, and the simple-git dependency itself. No lane researched git CVEs or simple-git advisories; the code map only listed hardening flags as untested ideas.
Why: The planned gate sits at service.ts:808 (after materialization). Everything git does while cloning a hostile repo (submodules, symlinks, hooks, filters, protocol helpers) happens earlier, so a malicious source can win before the security layer is even invoked. AgentPM also takes locators/refs from untrusted places (registry index 'repo', committed agentpm.yaml, skills.sh bridge).
Found: (1) Real clone-time RCEs exist and are exploited: CVE-2024-32002 (submodule + symlink on case-insensitive filesystems, i.e. Windows/macOS, writes into .git/hooks and executes on clone) and CVE-2025-48384 (CR in .gitmodules path -> hook write; added to CISA KEV 2025-08-25; macOS/Linux; fixed in git 2.43.7/2.44.4/2.45.4/2.46.4/2.47.3/2.48.2/2.49.1/2.50.1). Published mitigations: patched git, submodule.recurse=false, core.hooksPath to a safe dir, protocol allow-list. 'agentpm doctor' should check a minimum git version. (2) simple-git had THREE 2026 RCE advisories (verified via gh api advisories): CVE-2026-28292 critical (<3.32.3, case-insensitive protocol.allow bypass), CVE-2026-28291 high (<3.32.0), CVE-2026-6951 high (<3.36.0, '--config' not blocked -> protocol.ext.allow=always + ext:: source). D:\DevProjects\private\agentpm\packages\git\package.json declares "simple-git": "^3.28.0" (range includes all vulnerable versions); pnpm-lock.yaml currently resolves 3.36.0 (patched). Raise the floor to >=3.36.0. (3) More important: AgentPM's clone, ls-remote and fetch do NOT go through simple-git at all; they use raw spawn('git', args) (D:\DevProjects\private\agentpm\packages\git\src\index.ts:100, :146, :184, :202), so simple-git's blockUnsafeOperations plugin gives zero protection there. There is no '--' end-of-options separator and no leading '-' rejection anywhere in packages/git, packages/shared or service.ts (grep verified). A locator such as '--upload-pack=...' is the classic CVE-2022-24433 class. Not exploited/tested by me; code-derived. (4) Local git 2.54 docs confirm defaults: http/https/git/ssh = always, ext = never, everything else incl. file = 'user', and 'user' is only blocked when GIT_PROTOCOL_FROM_USER=0. AgentPM should set GIT_PROTOCOL_FROM_USER=0 plus an explicit protocol allow-list for locators that did not come from the user's own command line. (5) Design consequence the lanes missed: AgentPM already clones with --no-checkout, so the structural part of the scan can run on git OBJECTS before checkout: 'git ls-tree -r' exposes mode 120000 (symlink) and 160000 (gitlink/submodule), .gitmodules, .gitattributes (filter=/eol=), .lfsconfig, path collisions and sizes without materializing anything, identically on every OS. Block there, then check out.
Sources: https://github.com/advisories/GHSA-hffm-xvc3-vprc ; https://github.com/advisories/GHSA-r275-fr43-pm7q ; https://github.com/advisories/GHSA-jcxm-m3jx-f287 ; https://www.codeant.ai/security-research/security-research-simple-git-remote-code-execution-cve-2026-28292 ; https://securitylabs.datadoghq.com/articles/git-arbitrary-file-write/ ; https://dgl.cx/2025/07/git-clone-submodule-cve-2025-48384 ; https://www.wiz.io/vulnerability-database/cve/cve-2024-32002 ; https://security.snyk.io/vuln/SNYK-JS-SIMPLEGIT-2421199 ; https://git-scm.com/docs/git-config (protocol.allow, core.symlinks; text verified in local git 2.54.0 docs)

## Cross-platform determinism was assumed, not designed: neither the content digest nor the scanner verdict is reproducible across Windows/macOS/Linux or even across Node 24.x patch releases as currently proposed.
Why: A committed lock integrity computed on Linux that fails on a Windows teammate (the owner develops on Windows 11) will be 'fixed' by disabling verification. A client pre-push verdict that differs from the server verdict for the same bytes breaks the 'same engine at three gates' promise and the 'deterministic' requirement.
Found: (1) Working-tree bytes are not canonical: git docs state the committed .gitattributes 'eol' attribute forces CRLF/LF in the working tree regardless of the user's core.autocrlf, and with text set and nothing configured the default is eol=crlf on Windows. So the skill author (or attacker) controls per-OS byte differences; forcing core.autocrlf=false on clone is not sufficient. AgentPM's git package sets no autocrlf/eol/symlink config at all (grep verified). (2) core.symlinks=false (what git-clone probes to on Windows without Developer Mode) checks symlinks out 'as small plain files that contain the link text', so an lstat-based scanner (recommended by three lanes) sees a symlink on Linux and a harmless text file on Windows: different findings, different tree hash, and a Windows publisher would pack a text file where POSIX had a link. Symlink detection for git sources must come from git tree modes, not the worktree. (3) The mutable-targets lane's 'Go h1-style manifest of sha256 mode path lines' is not what Go does: dirhash.Hash1 is 'hex sha256, two spaces, file name, newline', sorted with slices.Sort, no modes, no symlinks, newlines in names disallowed. Including mode breaks on Windows, where the code map itself notes the executable bit is never set. (4) Unicode tables drift inside one LTS line: Node 24.0.0 shipped ICU 77.1 (Unicode 16); Node 24.16.0 (2026-05-21) updated to ICU 78.3 (Unicode 17); Node 26 also ICU 78.3. Rules built on \p{Default_Ignorable_Code_Point}, \p{Script=...}, String.prototype.normalize('NFKC'), case folding or localeCompare can therefore give different results on client and server that both satisfy 'Node >= 24'. Fix: vendor explicit code point ranges (Tags, bidi, zero-width, variation selectors, confusables) as data inside the versioned rule pack, record unicodeVersion in rulesetVersion, sort by UTF-16 code unit / byte order only. (5) Practical shape: a SOURCE integrity defined over canonical content (git blob bytes via ls-tree/cat-file, or archive file bytes) that goes into the committed lock, plus a separate machine-local MATERIALIZED hash kept only in the AGENTPM_HOME db for tamper detection of the linked copy. Never put the worktree hash in the committed lock.
Sources: https://git-scm.com/docs/gitattributes ; https://pkg.go.dev/golang.org/x/mod/sumdb/dirhash ; https://nodejs.org/en/blog/release/v24.0.0 ; https://nodejs.org/en/blog/release/v24.16.0 ; https://github.com/nodejs/node/pull/62324 ; https://github.com/vercel-labs/skills/issues/781

## Consent integrity: who is allowed to say 'yes'? The lanes never addressed (a) that the CLI operator is often an AI agent (AgentPM ships the agentpm-manage-skills skill that tells agents to run agentpm), (b) that a committed lock/approval file is attacker-controlled when the repo itself is untrusted, (c) what non-interactive mode should do other than 'fail'.
Why: A gate that a prompt-injected agent can satisfy with --yes / --allow-finding, or that a malicious repo can pre-satisfy by committing a matching lock + approvals, is decorative. 'agentpm sync' today hard-codes yes:true and is exactly what someone runs after cloning a stranger's repo.
Found: Precedents found: (1) direnv and mise bind approval to a CONTENT HASH and store it OUTSIDE the repository in user-local state; any edit requires re-approval. mise 'paranoid' mode additionally disables 'automatic trust for execution commands and the usual CI trust exemption'. This is the right model for 'cloned an untrusted project, ran agentpm sync': the committed agentpm.yaml/lock can carry integrity and the declared capability set (reviewable in PRs), but the decision 'I trust this contract' must live under AGENTPM_HOME keyed by project realpath + lock digest. (2) skil-lock keeps approvals IN git (.skil-lock-approvals.yaml with reviewer, reason, optional pr: scope). That works for PR review of your own repo but is the wrong trust root for foreign repos; both layers are needed. (3) Lockfile-injection literature (Snyk, lockfile-lint): reviewers skip lockfile diffs and tools like CodeRabbit are configured to ignore them, so 'lock integrity matches -> allow without prompting' (code map sync hook) lets a PR that changes source + integrity together pass silently. Mitigation: lockfile-lint style policy (allowed hosts/schemes for sources in lock) and show the capability delta, not the hash, in review. (4) Non-interactive behaviour in package managers (Nesbitt, 2026-06-05): pnpm strictDepBuilds fails the install; npm 11.16 allowScripts entries are version-pinned in package.json; Composer 'installs the package but skips executing its plugin code'. The Composer model maps well to AgentPM: in --yes/--json/non-TTY, materialize into the cache (quarantined, not linked), return a distinct exit code and a structured JSON list of held-back skills. (5) pnpm advisory GHSA-379q-355j-w6rj: git-hosted dependencies bypassed the script allowlist from 10.0.0 to <10.26.0 because a separate fetch code path never consulted it. AgentPM has the same shape: pull/adopt go through linkSkillIntoAgents (service.ts ~2346-2662), not the install gate at service.ts:808. One choke point or an explicit test per path. (6) Agent-driven installs are already exploited: Aikido (2026-02-20) found hallucinated npm package 'react-codeshift' originating in 'a single commit of 47 LLM-generated Agent Skills', spread to 237 repos, and after the researcher registered it the downloads continued because 'AI agents following skill instructions [are] triggering npx installs'. Name-only 'agentpm install <name>' across all sources has the same slopsquat exposure. Honest limit: an agent with shell access can also write the user-local trust store; mitigate with a separate 'agentpm approve' command that refuses non-TTY stdin, and document a Claude Code deny rule for it.
Sources: https://mise.jdx.dev/paranoid.html ; https://mise.jdx.dev/cli/trust.html ; https://nesbitt.io/2026/06/05/install-script-allowlists.html ; https://github.com/pnpm/pnpm/security/advisories/GHSA-379q-355j-w6rj ; https://github.com/skills-lock/skil-lock ; https://snyk.io/blog/why-npm-lockfiles-can-be-a-security-blindspot-for-injecting-malicious-modules/ ; https://github.com/lirantal/lockfile-lint ; https://www.aikido.dev/blog/slopsquatting-ai-package-hallucination-attacks

## Nobody measured the proposed BLOCK / REQUIRE-PIN defaults against a benign corpus. I measured the most obvious one (anthropics/skills, 177k stars, pushed 2026-09-10) via the GitHub tree and code-search APIs.
Why: Several lanes recommend default BLOCK for archives, binaries, office documents, raw branch URLs, unpinned npx/pip, and 'fetch-and-follow' instructions, while the deterministic-detection lane sets a target of about 0% false BLOCKs on anthropics/skills. Both cannot hold. A gate that blocks Anthropic's own flagship skills will be switched off on day one.
Found: anthropics/skills tree (419 blobs): 54 .ttf font binaries, 117 .xsd, 1 .pdf (skills/theme-factory/theme-showcase.pdf), 1 nested ARCHIVE (skills/web-artifacts-builder/scripts/shadcn-components.tar.gz), 26 files with mode 100755, 0 symlinks. skills/mcp-builder/SKILL.md line 61/65: 'Use WebFetch to load https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/README.md' (a mutable branch raw URL the agent is told to fetch and follow), line 141: 'npx @modelcontextprotocol/inspector' (unpinned launcher), lines 41-43 tell the agent to crawl modelcontextprotocol.io. skills/claude-api/SKILL.md repeatedly instructs 'WebFetch the relevant SDK repo from shared/live-sources.md'. Code search: 27 files mention curl, 32 mention WebFetch, many unpinned 'pip install' lines in prose (pdf, slack-gif-creator, mcp-builder, claude-api). So first-party skills contain exactly the owner's feared pattern (mutable external instruction source), legitimately. Separately, skil-lock's own ecosystem scan reports 38.8% of 17,065 public skills execute shell commands but only 4.0% declare it in frontmatter, so the threats lane's 'declared-vs-observed capability mismatch as a hard fail' would fail roughly a third of the ecosystem. Practical policy: BLOCK only fetch-and-EXECUTE (pipe to shell, iwr|iex), hidden-channel Unicode, escaping symlinks, bytecode without source; everything else (mutable URL the agent is told to read, unpinned launcher, archive, binary) is REVIEW with a host allowlist (modelcontextprotocol.io, raw.githubusercontent.com/<org> ...) and a per-digest acceptance, and the residual risk is carried by pin + capability-delta re-approval. Build the benign fixture set first and tune against it before shipping any BLOCK default.
Sources: https://github.com/anthropics/skills ; https://github.com/anthropics/skills/blob/main/skills/mcp-builder/SKILL.md ; https://github.com/anthropics/skills/blob/main/skills/claude-api/SKILL.md ; https://github.com/skills-lock/skil-lock

## Host coverage stops at Claude Code and Codex. AgentPM's 'generic' target writes to .agents/skills, which is read by about 15 other hosts with different precedence and trust rules, and VS Code now consumes Claude-format plugins too.
Why: A skill that is inert under Claude Code semantics can behave differently elsewhere; a global generic install fans out to every one of those agents at once; and name shadowing is a deterministic, checkable attack that no lane turned into a rule.
Found: (1) agentskills.io client guide: .agents/skills is the cross-client convention at project and user scope; 'project-level skills override user-level skills' is 'the universal convention'; a trust check for project skills is only something clients should 'consider'; validation is deliberately lenient (name/dir mismatch or >64 chars: 'warn, load anyway'). (2) Clients reading .agents/skills per a mid-2026 survey: Codex, Gemini CLI, Antigravity, Cursor, VS Code Copilot, Zed, Devin, Warp, Amp, Roo Code, Kilo Code, Junie, Factory, Goose, OpenCode. Claude Code does not. The same source says allowed-tools is honoured only by Claude Code and GitHub Copilot (outside VS Code), and disable-model-invocation by Claude Code, VS Code Copilot, Cursor and Zed (secondary source, medium confidence). (3) Gemini CLI docs: precedence built-in < extension < user (~/.gemini/skills or ~/.agents/skills) < workspace; within a tier '.agents/skills/ alias takes precedence over .gemini/skills/'; consent prompt on every activation plus install consent for remote URLs. A search snippet claimed workspace skills load only in trusted folders, but I could NOT find that sentence on either official page: unverified. (4) VS Code 'agent plugins': plugin.json with the agent-plugins.org 1.0.0 schema, bundles skills, agents, MCP servers, hooks, slash commands; 'VS Code discovers plugins from the Copilot and Claude plugin formats'; checks for plugin updates automatically every 24 hours; docs warn that plugins 'can include hooks and MCP servers that run code on your machine'. Consequences for the scanner: (a) add a deterministic SHADOWING finding: AgentPM knows every installed name across .claude/.codex/.agents/.gemini dirs and both scopes, so an install whose name collides with an existing skill from a different source in a higher- or equal-precedence location should require confirmation; (b) evaluate capability fields against the union of host semantics rather than the target adapter only; (c) treat global generic installs as the highest blast radius tier; (d) a Claude-format plugin placed by AgentPM may also be picked up and auto-updated by VS Code outside AgentPM's gate.

## The 15-row mutable-reference catalogue misses dependency declarations INSIDE bundled scripts, above all PEP 723 inline metadata executed by 'uv run', plus index/registry overrides and non-existent (hallucinated) package names.
Why: 'uv run scripts/foo.py' is the idiomatic way skills ship Python helpers. The command line contains no package name at all, so rules that look for 'uvx pkg' / 'pip install pkg' never fire, yet every run resolves fresh, unpinned packages from the network: a rug-pull channel with immutable skill bytes.
Found: PEP 723 lets a script declare dependencies in a '# /// script' TOML comment block; uv auto-installs them on 'uv run'. SafeDep (2025-08-01): SCA tools do not look there ('your SCA tool didn't find anything because it never looked there in the first place') and such scripts are 'rarely reviewed in detail'. uv docs: 'uv lock --script' creates an adjacent lock file (example.py.lock) that later 'uv run --script' reuses; a [tool.uv] exclude-newer RFC 3339 timestamp limits resolution to distributions released before that date; 'uv add --index <url> --script' writes an ALTERNATIVE PACKAGE INDEX into the inline metadata, which is the same registry-redirect primitive Trail of Bits used in its fourth bypass. Deterministic, offline checks to add: parse every '# /// script' block; classify each requirement (== exact vs range vs bare); require either exact pins plus an adjacent <script>.lock or exclude-newer, otherwise emit a mutable-dependency finding; flag any index/extra-index/registry override (inline [[tool.uv.index]], pip --index-url/--extra-index-url, npm --registry, bundled .npmrc / pip.conf / uv.toml) as high severity; same for requirements.txt without hashes and package.json without a lockfile next to bundled scripts. Hallucinated package names (Aikido: 'react-codeshift' born in 47 LLM-generated skills, 237 repos) cannot be verified offline; offer it only as an optional online existence/age check and list every referenced package name in the external-reference inventory so a human sees it.
Sources: https://peps.python.org/pep-0723/ ; https://safedep.io/pep-723-inline-metadata-security/ ; https://docs.astral.sh/uv/guides/scripts/ ; https://www.aikido.dev/blog/slopsquatting-ai-package-hallucination-attacks ; https://blog.trailofbits.com/2026/06/03/the-sorry-state-of-skill-distribution/

## The audit-runtime gap: every proposed integrity control (lock, doctor, verify, drift detection) only executes when someone runs agentpm. The host loads skills straight from disk with AgentPM out of the loop, and Claude Code reloads edited SKILL.md live. No lane looked for a load-time enforcement point.
Why: The code map's top risk is that a prompt-injected agent with file-write tools edits the cached/linked skill in place. With symlink/junction installs into a shared cache this affects every linked project, and nothing notices until the next manual 'agentpm doctor'. Read-only attributes do not stop a same-user process, least of all on Windows.
Found: (1) The problem has a name and a paper: 'Sealing the Audit-Runtime Gap for LLM Skills' (arXiv 2605.05274, submitted 2026-05-06, revised 2026-09-03) argues audits happen before deployment with no guarantee the runtime artifact matches, and proposes a mandatory 'Skill Verification Loader' that verifies integrity at load time (batched verification under 86 ms on 1,023 skills). Their registry is on-chain/DAO based and not applicable, but the loader idea and the latency number are. (2) Claude Code hooks reference: PreToolUse can match the 'Skill' tool and CAN block; SessionStart cannot block (context only); ConfigChange (matcher 'skills') and FileChanged exist but cannot block; there is no SkillLoaded event; InstructionsLoaded covers CLAUDE.md/rules only. The tool_input schema for the Skill tool is not documented, so the skill name field must be confirmed by testing. (3) Prior art: mannanj/skillguard (skillguard.sh) uses a PreToolUse hook that refuses 'changed or unscanned targets' at invocation time and records decisions in SQLite; license is AGPL with a commercial option, so inspiration only. skil-lock explicitly lists 'No runtime guard / Claude Code hooks integration' as out of scope. (4) Feasible AgentPM feature: an opt-in 'agentpm guard' that, after explicit confirmation (it edits agent settings), registers a user-level PreToolUse(Skill) command hook calling a fast hash-only 'agentpm verify --skill <name>' (deterministic, offline, millisecond range) and denies on mismatch. Limits to state honestly: skill descriptions are already in context before any hook fires; the model can Read a SKILL.md without the Skill tool; Codex hooks are hash-trusted separately and Gemini/other .agents/skills hosts have no equivalent, so there the only mitigations are copy-instead-of-link installs plus scheduled verify.
Sources: https://arxiv.org/abs/2605.05274 ; https://code.claude.com/docs/en/hooks ; https://skillguard.sh/ ; https://github.com/mannanj/skillguard ; https://github.com/skills-lock/skil-lock

## CONTRADICTIONS
- Registry checksum: the code map (client-install-flows) calls it a 'cheap win' because 'the server checksum is sha256 of the exact serialized file it serves (SRV:464-475), which is what the client already hashes'. The supply-chain lane says the two hashes can never match. I read the code: D:\DevProjects\private\agentpm\packages\registry-server\src\server.ts:464-475 hashes and stores compact JSON.stringify(archive), but the download route (:581-583) re-parses the file and sends it through sendJson, which pretty-prints with JSON.stringify(body, null, 2) (:70-71). The supply-chain lane is right; the 'cheap win' only exists if the server streams the stored bytes verbatim.
- Digest definition: three incompatible constructions are recommended. mutable-targets: 'Go h1-style manifest of sha256 mode path lines with explicit symlink entries' (real Go h1 has neither mode nor symlinks, and mode cannot be derived on Windows, as the publish-flows code map itself notes). supply-chain: per-file sha256 -> tree digest -> sha256 of canonical JSON of {name, version, kind, target, treeDigest} (mixing metadata into the digest breaks content-addressed dedupe and OMS-style tree signatures). gh skill precedent: git tree SHA (SHA-1, git sources only). One construction must be chosen, and it must be defined over canonical source bytes, not the CRLF/symlink-dependent worktree.
- Where provenance lives: deterministic-detection and supply-chain additions say AgentPM should interoperate with / read-write the 'gh skill' provenance frontmatter inside SKILL.md; the mutable-targets lane says trust records must live outside the skill. Writing into SKILL.md also changes the tree hash that was just pinned and makes the installed copy differ from the registry digest.
- Default BLOCK policy vs false-positive target: deterministic-detection wants about 0% false BLOCKs on anthropics/skills, while threats, mutable-targets and supply-chain lanes recommend BLOCK / REQUIRE-PIN for raw branch URLs, unpinned npx/pip, releases/latest, archives, office docs, binaries, and 'make fetch-and-obey a block rule at the registry gate'. Measured: anthropics/skills ships 54 .ttf, a .pdf, a .tar.gz, 26 executable files, and mcp-builder tells the agent to WebFetch raw.githubusercontent.com/.../main/README.md and run 'npx @modelcontextprotocol/inspector'. The mutable-targets verifier already warned that the row-level policies are unvalidated proposals.
- Declared-vs-observed capability mismatch 'as a hard fail' (threats lane, server-side) versus skil-lock's measurement that 38.8% of 17,065 skills run shell commands while only 4.0% declare it. A hard fail would reject a large share of legitimate skills.
- Reserved names: the host-capability lane says the registry should enforce 'no anthropic or claude in skill names'; the deterministic-detection verification shows this is a claude.ai/API upload rule only, that Anthropic's own bundled skill is named 'claude-api', and recommends WARN.
- ATR usage: deterministic-detection recommends vendoring 'rules/skill-compromise plus the stable-maturity rules' and quotes a 0.24% FP rate; its own verification and the existing-scanners lane show all 38 scan_target:skill rules are maturity:test, the enforce lane detects 0 of 32 malicious SKILL.md samples, and the FP figure does not apply to any skill rule. Version facts also disagree: repo 4.1.0 vs npm latest 4.0.0 vs Cisco-vendored 3.5.6.
- Verdict vocabulary: PASS/REVIEW/BLOCK (existing-scanners), PASS/FAIL/INCOMPLETE (threats, wrongly attributed to OWASP; it is Adversa's), pass|fail|error with error=reject (supply-chain), BLOCK/NEEDS-APPROVAL/WARN/INFO (deterministic-detection), allow|warn|confirm|block (code map), pass/warn/block (host-capability). They also disagree on what 'unanalyzable' means: reject outright vs needs approval.
- Trust root for approvals: mutable-targets says approvals are stored outside the skill and non-interactive runs fail unless pre-approved; host-capability says CI should pass when 'that exact capability digest is already approved in the committed contract'; the code map makes sync 'lock-driven: integrity match -> allow without prompting'. For a freshly cloned untrusted repo the committed contract and lock are attacker-controlled, so they cannot be the approval. Related: the code map wants provider installs to require a confirmation 'never satisfied by --yes alone' while sync hard-codes yes:true and CI needs a non-interactive path.
- Immutable link targets vs AgentPM's own workflows: host-capability says 'link agent directories only to an immutable content-addressed copy' and mutable-targets says snapshot local sources by default; but pull/adopt/push are built around one mutable shared library directory per skill that users edit and push to a git vault, and best-effort read-only has no effect against a same-user process on Windows. Snapshots break the edit -> push loop unless a live dev mode is first-class.
- Scan what the skill points to vs never fetch: the threats lane quotes Air Security ('it has to be scanned for everything it points the agent to'); the existing-scanners and deterministic-detection additions show scan-time fetching is defeated by cloaking (reviewer bait-and-switch). The proposed alternative, 'vendor a snapshot of external docs at publish', needs network access at publish time, which conflicts with the offline/deterministic requirement, and raises third-party copyright questions nobody addressed.
- Trail of Bits timing: the threats lane and the mutable-targets addition say each bypass took under an hour; two verifications show it was under one hour total for three of four skills and 'a few hours' for the LLM-judge injection; the 'each' wording comes from OWASP AST08's paraphrase. Also NVIDIA SkillSpector was tested by Air Security and Adversa, not by Trail of Bits.
- Claude Code marketplace updates: threats lane says plugins 'auto-update silently with no integrity check'; its verification says third-party marketplaces have auto-update off by default and the community marketplace pins commit SHAs; the host-capability addition says those SHA pins are auto-bumped by CI, so the pin is integrity-per-version, not protection against a later malicious commit. Three different pictures of the same control.
- Plugin MCP servers: host-capability summary says they 'start automatically without approval'; its own verification shows project-scope skills-directory plugins go through per-server approval and monitors do not load. Only marketplace-installed and personal-scope plugins are ungated.
- SkillSpector facts: '64 patterns in 16 categories' (threats addition, via OWASP) vs '71-pattern table' (supply-chain addition); and '--no-llm' is described as fully static/offline while SC4 still sends dependency names to OSV.dev.
- Existing TypeScript engines: existing-scanners says none is TS/MIT and the supply-chain addition says 'nothing credible exists' in TypeScript, while verification found affaan-m/agentshield (TypeScript, MIT, 1.2k stars, 268 deterministic rules) and the threats addition lists opena2a-org/hackmyagent (TypeScript, Apache-2.0). The build-your-own conclusion survives, but the absolute claim does not.
- Symlink handling: several lanes say use lstat and block escaping symlinks; on Windows with core.symlinks=false git materializes symlinks as plain text files, so the same repo yields different findings and hashes per OS. This contradicts the 'same deterministic verdict at all three gates' goal unless symlinks are read from git tree modes.
